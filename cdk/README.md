## Search-term export permissions

The Airflow DAG in `guardian/ophan-data-lake` uses `aws_feast_code` to copy BigQuery exports from GCS to S3. The existing `DynamicFronts/XAR` role (CloudFormation logical ID `DynamicFrontsXARCA695DED`, repository tag `guardian/recipes-backend`) owns the CODE permission. CDK embeds `feast-unifiedapi-datatransfer-code-s3-write` in that same role's `Policies` property alongside the unchanged `invokeFetcher` policy; it creates no separate IAM policy resource or role.

CODE receives `s3:PutObject` on `arn:aws:s3:::feast-unified-api-bqsearchterms-code/*`, with the existing `VisualEditor0` SID and no conditions or additional permissions. The policy name is retained for continuity, but deployment intentionally replaces its former `feast-unifiedapi-datatransfer-code/*` object scope with the new bucket; it does not grant access to both buckets.

PROD receives a new inline policy, `feast-unified-api-bqsearchterms-prod-s3-write`, on its own existing `DynamicFronts/XAR` role, granting only `s3:PutObject` on `arn:aws:s3:::feast-unified-api-bqsearchterms-prod/*`. Read-only AWS checks confirmed that `feast-PROD-recipes-backend-DynamicFrontsXARCA695DED-ztEKAQkzxwug` belongs to the PROD stack and `guardian/recipes-backend`, with only `invokeFetcher` inline and no managed policies attached. There is no existing PROD export policy to take over. Each stage's role receives only its own bucket permission; other stages receive no search-term export policy. Existing trust policies and `invokeFetcher` remain unchanged.

### Deployment and migration

1. Before deployment, use read-only AWS calls with profile `feast` to confirm account `156041417282`, the stack's logical-to-physical role mapping, repository tag and current inline policies. The verified physical role is `feast-CODE-recipes-backend-DynamicFrontsXARCA695DED-yxG5lJ1rGztq`. Review the current policy against the intended bucket change and confirm that no other stack or policy resource manages the same role/policy-name pair. Coordinate the Airflow destination change to `feast-unified-api-bqsearchterms-code`; writes to the old bucket will no longer be permitted by this policy after deployment.
2. Run the CDK tests and synth. The app's default stack names differ from the verified live `feast-CODE-recipes-backend` and `feast-PROD-recipes-backend` names, so a default diff can misleadingly show an entirely new stack. From this directory, compare against the verified deployed template using `set -o pipefail; AWS_PAGER='' aws cloudformation get-template --stack-name feast-CODE-recipes-backend --region eu-west-1 --profile feast --query TemplateBody --output json --no-cli-pager | ../node_modules/.bin/cdk diff RecipesBackend-euwest-1-CODE --app cdk.out --template /dev/stdin --profile feast --no-change-set --path-metadata false --version-reporting false --ci`. Repeat with both CODE stage strings changed to PROD. `--no-change-set` prevents change-set creation. Resolve unrelated differences, including build-specific `IMAGE_TAG` values, and confirm each release targets the existing stack before deployment. The intended change is an in-place addition to each stage's existing role's `Policies`, with no role replacement.
3. Leave the console-added policy in place. CloudFormation documents inline role-policy updates as requiring no interruption, and IAM `PutRolePolicy` adds or updates a policy by role name and policy name. Keeping both names unchanged is intended to update the existing grant in place with the new bucket scope, not create a second grant. This is an update to an already-managed role, not a separate resource import. No pre-deployment deletion is required or intended.
4. An authorised operator must review and deploy each stage through the normal release process. For CODE, the live CloudFormation handler's treatment of the out-of-band policy has not been exercised here; in-place takeover is expected from the documented update semantics, not proven. PROD adds a new grant rather than adopting a manual policy; recheck its role policies before deployment for intervening changes. Uninterrupted exports also depend on coordinating each Airflow destination and IAM propagation. Check stack events and the exact policy after deployment, confirm `invokeFetcher` is unchanged, confirm there is only one export policy per role, and verify each Airflow export succeeds to its corresponding bucket. Do not delete the CODE named policy afterwards: it is the same policy now declared in CDK.
5. Treat rollback carefully: reverting the template to one without this policy may remove the previously manual grant once CloudFormation manages it. Investigate any failed update or rollback before retrying; do not remove or recreate the role or manually delete the grant as a migration step.

References: [CloudFormation inline role policies](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-iam-role-policy.html) and [IAM PutRolePolicy](https://docs.aws.amazon.com/IAM/latest/APIReference/API_PutRolePolicy.html).
